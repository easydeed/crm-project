TASK: OR-027
BRANCH: chore/v0-audit

OBJECTIVE
Read the v0 export and report exactly what is in it. No code changes.

WHY
The re-skin packets get written from this report. The export contains
screens we rejected, patterns this app cannot use, and markup that will
break existing tests. Knowing which is which before touching src/ is
what keeps the re-skin from undoing the build.

SCOPE
- Read reference/v0-export/ and report
- Out of scope: ANY change to src/, any import from reference/,
  any styling work

REPORT THE FOLLOWING

1. What is actually there
   The file tree at two levels. Which framework and version, which CSS
   approach (Tailwind version, CSS modules, inline), which component
   library if any. Whether it is app router or pages.

2. Design tokens — the concrete values
   Every color as it appears, with where it is used. The type scale:
   family, sizes, weights, letter-spacing. Spacing scale. Border radii.
   Shadows. Any CSS custom properties or Tailwind theme extension.
   Give me the actual values, not a description of them.

3. Screen mapping
   A table: every exported screen or route, and which src/ route it
   corresponds to, if any. Three buckets:
   - maps to a real screen (name both)
   - a /lab experiment we rejected (campaign builder, template gallery,
     audiences, automations, the full client page)
   - neither, and what it appears to be

4. The two signature components
   ParcelMap and the recorder stamp. For each: where it is, what props
   it takes, what it renders, whether it is presentational or reaches
   for data, and whether it could be lifted with only a props change.

5. What would break the browser checks
   Against e2e/checks.ts: interactive elements under 44px, text under
   15px carrying information, anything that would produce horizontal
   scroll at 390px. Be specific — component and value.

6. What would break the existing tests
   We have roughly a dozen tests asserting markup and copy, not just
   behavior. Find them yourself (grep the test files), list them, and
   say for each whether the export's version of that screen would still
   satisfy it. The ones I know of:
   - the delete confirmation copy
   - found-nothing as role="status", never role="alert"
   - add-on rows rendering identically on and off apart from the switch
   - /app allowing exactly three components
   - the plain-language ban list
   - the MLS framing copy
   Report any others you find.

7. What this app cannot use
   localStorage or sessionStorage, client-only data patterns, mock-array
   props, anything requiring a dependency we do not have. List each with
   the file it is in.

8. Your recommendation
   Which parts to harvest as-is, which to take as reference only, and
   which to ignore entirely. Propose a re-skin sequence: which screens
   in which order, and where you would start.

ACCEPTANCE CRITERIA
1. Every section above is answered with specifics, not summaries
2. No file under src/ is changed
3. No import from reference/ is added anywhere
4. The report names actual values, files, and line references

DO NOT
- Change any code
- Import anything from reference/
- Start the re-skin
